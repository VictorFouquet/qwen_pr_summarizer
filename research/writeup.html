A prompt-optimization loop can run for hours, commit every trial, and draw a tidy graph — while the model it is tuning never sees the prompt at all. This is the log of finding that out, fixing it, discovering the metric itself was wrong, and finally getting a small local model to write a genuinely good PR summary.

SETUP

One variable, everything else frozen

The system is a grounded PR summarizer: a local Qwen model reads a pull request through two tools, then writes a summary. A harness scores that summary and lets a researcher tune only the system prompt, so any change in the score is caused by the prompt alone.

ACT I

The loop was doing nothing

The first sign was eerie: the baseline scored 0.079, an edit scored 0.062, another edit scored exactly 0.062 — with byte-identical summaries for two of the three PRs. Different prompts cannot produce identical greedy output unless the model isn't conditioning on them.

The cause was mundane and total. Ollama's default context window is 2048 tokens. The tool output for these PRs is 24,000–38,000 tokens. When the input overflows, llama.cpp keeps the tail and discards the head — and the system prompt sits at the head. The model was reading the end of a diff and none of its instructions.

ACT II

Getting onto the GPU without buying one

Raising the window meant the model had to run fast. But the machine's Ollama was the snap build, which was pinned 100% to CPU.

Two blockers, no root access: snap confinement never staged the NVIDIA libraries, and the newer Ollama's CUDA needs a driver 550+ (the box has 535). The way through was a userspace Ollama on the Vulkan backend, pinned to the discrete GPU and reusing the model already on disk — no sudo, no download of the 5 GB model, and with q8_0 KV-cache quantization so a 32k window fits in 8 GB. Result: a trial went from 28 minutes to ~12, and the loop could finally iterate.

ACT III

Optimizing the wrong thing

With the prompt finally visible, the score climbed fast — 0.058 to 0.404, a 7× gain over ten trials. It was also, in hindsight, the model getting worse at its actual job.

The original metric rewarded coverage: the fraction of changed filenames the summary echoes. So the optimizer learned to echo filenames. Each winning edit pushed the model further from prose and toward a file manifest — faithful, dense, and useless as the thing a reviewer actually reads.

A rising number meant a worse summary. The metric was measuring the wrong thing, faithfully.

Two behaviours showed up repeatedly and are worth remembering: negative examples backfire — telling the model “don't write agents/teams” primed it to emit exactly that — and the model is extremely fragile to wording: an instruction that helped the 21-file PR routinely broke the 70-file one.

ACT IV

Scoring against the real thing

If the job is to write a PR body, the honest measure is: how close is the summary to the PR body a human actually wrote? Every eval PR already has one — so it becomes a held-out answer key.

The new signal is body-similarity: cosine distance between an embedding of the summary and an embedding of the real PR description (a local nomic-embed-text model), rescaled so vague filler ≈ 0 and a faithful body ≈ 1. It's deterministic and reference-based — a stable optimization target, unlike an LLM judge. Faithfulness stays as the anti-hallucination gate; coverage is kept only as a diagnostic.

Before trusting it, it was validated on the summaries already in hand — and it did the right thing: it preferred earlier prose summaries over the later filename-list ones, and floored vague text.

The reframe cost the old “7× improvement” its meaning — the two experiments measure different things and share no scale. So v1 was archived and v2 restarted from trial 1.

ACT V

The diff was mostly noise

Under the new metric the seed prose prompt already scored 0.63 — the model writes decent PR bodies on its own once you stop rewarding filenames. Two of three PRs were near-perfect. One was stuck.

PR #11 (a 70-file web app) sat at body-similarity 0.53 and code-dumped 665 words no matter the prompt. It still overflowed the 32k window — so its prompt was still being truncated. The reflex was “needs a bigger GPU.” The real answer: half of that diff was a single 19,000-token design-plan markdown, plus lockfiles and config. None of it belongs in a summary.

Capping every file's patch to 120 lines and dropping lockfile bodies shrank the grounding below the window — and the effect on #11 was immediate and total.

One tool change — no new hardware, no prompt edit — took the composite from 0.68 to 0.91, brevity to a perfect 1.0, and turned #11 into the best-scoring summary of the three. A leaner diff is simply a better thing to summarize.

TAKEAWAYS

What actually moved the needle

01 · infrastructure

Check the model reads the prompt

Determinism was the smoking gun: identical output across different prompts at temperature 0 means the prompt is being truncated. No amount of prompt tuning matters until it's in the window.

02 · measurement

Optimize the goal, not a proxy

Filename-coverage was easy to measure and easy to game. Scoring against the real PR body — the actual artifact — realigned the loop with the job in one change.

03 · input quality

Trim the input before the model

The single biggest win wasn't a prompt at all. Half of one diff was a design doc; capping patches unblocked the hardest PR and improved every other one.

04 · model behaviour

Small models are wording-fragile

Negative examples prime the forbidden token; a fix for one PR breaks another. Short, general, positive instructions held up; clever ones didn't.
